# Toshiba IoLIFE Refrigerator (Local)

> **English summary**
> An unofficial Home Assistant custom integration that reads Toshiba IoLIFE refrigerators (type `0xCA`, `55 AA CC 33` frames) directly over the LAN, with push updates for doors and the ice maker's water shortage.
> It uses your IoLIFE account only to fetch the local token/key (at setup and re-authentication); everything else stays on your LAN.
> Only tested with a Japanese GR-Y540XFS. Other models may not work. Provided as is, without support guarantees.
> No need to set up the built-in Midea integration. Install via HACS (custom repository) or copy `custom_components/toshiba_iolife_fridge` to `/config/custom_components/`.

**東芝の公式ソフトウェアではありません。** 動作を確認したのは GR-Y540XFS（日本向け）だけです。ほかの機種で動くかは分かりません。不具合の報告は歓迎しますが、対応は保証できません。

東芝の IoLIFE 対応冷蔵庫（確認機種: GR-Y540XFS）の状態を、LAN 内から直接読み取って Home Assistant のセンサーにするカスタム統合です。
スマホアプリに届く「給水不足」などを、クラウドを経由せずに HA で扱えるようにすることが目的です。

## 背景

HA 2026.8 以降の Midea 統合（Toshiba Lifestyle）では、IoLIFE アカウントでのログインとローカル通信用の鍵（token/key）の取得、冷蔵庫との認証までは成功します。
ところが、状態の問い合わせでは失敗します。原因は電文の形式です。

- Midea 標準の冷蔵庫は `AA` で始まる電文を使う
- 東芝の IoLIFE 冷蔵庫は `55 AA CC 33` で始まる独自の電文を使う（IoLIFE アプリの定義ファイル `T_0008_2500_CA_8.lua` に準拠）

この統合は、認証と暗号化には midea-local をそのまま使い、中身の電文だけを東芝形式で組み立てます。

表示名は IoLIFE アプリの呼び方に合わせています。
庫内の実温度は、通信内容にもアプリにもありません（冷蔵室・冷凍室は 5 段階の温度設定のみ）。

2026-09-30 にアプリで設定を変えて確認した値の対応：温度設定は中＝12・1 段強＝17、節電モードは節電オフ＝0・かってにエコ＝2・とってもエコ＝4。とってもエコの間は温度設定の値が 0x80 になる。

2026-09-30 16:09〜16:19 にアプリで全モードを切り替えて、次の対応も確認した：温度設定の弱＝2・強＝22、上段冷凍室の急冷凍＝1・粗熱取り＝6・お好み冷却＝8・冷凍ごはん＝9、チルドルームの氷結晶＝1・Deli＝2・解凍＝0x22、製氷の一気製氷＝1・製氷オフ＝2、UV 除菌オン。チルドルームの氷結晶・Deli・解凍モードの間は、冷蔵室の温度設定も 0x80（自動制御）になる。お好み冷却中は本文 20 バイト目に 20 が入る（時間の設定値と思われる。統合では未使用）。

### 更新のしかた

冷蔵庫とは接続をつなぎっぱなしにしています（10 秒おきにハートビートを送信）。

- **冷蔵庫からの通知**：冷蔵庫は、ドアの開閉（ドア情報）や状態全体を自分から送ってきます。ドアは開け閉めした瞬間に反映されるので、数秒の開閉も取りこぼしません。
- **定期問い合わせ**：念のため、60 秒おきに状態全体も問い合わせています。
- **切断時**：5 秒→10 秒→30 秒→60 秒と間隔を空けて、自動でつなぎ直します。3 回続けてつながらなければエンティティを利用不可にします。正常に状態を受け取るまでの間に認証エラーが合計 3 回起きたら、再認証を求めます（間に通常の通信エラーが挟まっても数え直しません）。
- **状態の鮮度**：ハートビートに応答があっても、状態全体が 150 秒届かなければ利用不可にしてつなぎ直します。
- **鍵の不一致**：冷蔵庫の再登録などで鍵が変わると、認証の段階で署名不一致になります。これを認証エラーとして数え、正常に状態を受け取るまでに合計 3 回起きたら再認証を求めます。

ドア情報の通知（function 0x22）は、状態全体（0x00）とビットの並びが違います（野菜室が bit1、冷凍室上段が bit3、冷凍室下段が bit4）。

### 実機で確認したこと

- 給水タンクを空にすると、スマホの給水不足通知とほぼ同時に製氷状態が「給水不足」になる。
- 給水後すぐには戻らず、次の製氷サイクルで「製氷中」に戻る（実測で約 50 分後）。
- 消費電力と消費電力量は、定義ファイルの記述と違ってリトルエンディアンで読むのが正しい。消費電力はスマートプラグの実測と連動するが、コンプレッサー運転中は 1.3〜1.4 倍ほど大きく出る。正確な電力はスマートプラグで測ること。
- 消費電力量（本文14〜15バイト目、Wh）は「直近24時間の消費電力量」で、毎時59分ごろに更新される。0時にリセットされる当日の値ではないので、時刻によって増えも減りもする。2026-10-07〜10 にスマートプラグの直近24時間の実測と比べ、±10% 程度で一致した（当初「0時リセットで実測の1.3倍」としていたのは、比較相手をスマートプラグの当日値にしていた誤り）。
- この値が正しいのは問い合わせへの応答（data type 0x03）だけ。冷蔵庫からの自発通知（0x04）の同じ位置には、何時間〜何日も変わらない古い値が入っているため使わない。積算の長期統計（`TOTAL_INCREASING`）の対象にもしていない。
- ドアの値は 1 が「開」。冷蔵室ドアを 5 秒ほど開け閉めすると、その瞬間ごとに冷蔵庫からドア情報の通知が届く。
- 冷蔵室・冷凍室・冷凍室上段・製氷室・野菜室のすべてのドアで、開閉がスマホアプリと同時に HA に反映されることを確認済み。
- 外気温は冷蔵庫本体の周囲温度センサーの値で、置いている部屋の温度の目安になる（本体の放熱などでやや高めに出ることがある）。
- ドアの開けっぱなし警告が鳴ると、エラーコードが一時的に 401 になり、閉めると 0 に戻る。

### 未確認のこと

- 上段冷凍室モードの値 7（定義ファイルでは cool_cooking。この機種のアプリには対応する選択肢がない）
- 高温警告のビットが実際にどう送られてくるか（ドア情報の通知の 2 バイト目。定義ファイルどおりに実装）
- かってにエコの運転情報の通知が届く間隔（問い合わせには応答しない）
- 節電モードの値 1・3（この機種のアプリには対応する選択肢がない）
- 温度設定の「やや弱」の値（弱＝2・中＝12・やや強＝17・強＝22 の 5 刻みから 7 と推定）

## 導入

1. HACS の「カスタムリポジトリ」にこのリポジトリ（種類は Integration）を追加してインストールするか、`custom_components/toshiba_iolife_fridge` を HA の `/config/custom_components/` にコピーする。そのあと HA を再起動する。
2. 「設定 → デバイスとサービス → 統合を追加」で「Toshiba IoLIFE Refrigerator (Local)」を選ぶ。
3. IoLIFE アカウント、パスワード、冷蔵庫の IP アドレスを入力する。

設定フローでは IoLIFE にログインして鍵を取得し、その鍵で冷蔵庫が実際に応答することを確かめてから登録します。
保存するのは鍵だけで、パスワードは保存しません。
冷蔵庫の再登録や Wi-Fi の設定し直しで鍵が変わった場合は、HA から再認証を求められるので、もう一度ログインしてください。

HA 本体の Midea 統合を設定する必要はありません。IoLIFE へのログインと鍵の取得も、この統合だけで行います。
依存ライブラリの midea-local は、HA が manifest の指定に従って自動で入れます。

機種名（GR-Y540XFS など）は登録時に IoLIFE から取得します。0.1.0 で登録した場合は内部コードが入っていたため、0.2.0 以降では空欄になります。機種名を表示したい場合は、統合を削除して登録し直してください。

## 開発

```bash
python -m pip install midea-local pytest
python -m pytest tests
```

`tests/test_protocol.py` は、実機から取得した応答電文を使って解析処理を確認します（HA は不要です）。
